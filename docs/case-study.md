# Laser remnant inventory: turning offcuts back into material

*Draft for the Notion portfolio page. Synthetic data, real use case.*

**Tools:** Python · Excel · Power BI · Power Query · DAX · TMDL / PBIR (report as code)
**Repository:** github.com/lucasnunesf/laser-remnant-inventory

---

## Context

AC Metais is a Brazilian metal fabrication company: laser cutting, welding/boilermaking, finishing and shipping. Every steel, stainless or aluminum sheet that goes through the laser leaves a remnant, an offcut that can still be used for smaller parts.

## Problem

Nobody controlled the remnants:

- they were dropped on the shop floor without an address;
- planners did not know what was in stock, so they cut new sheets instead;
- old pieces were cleared out in cleanup campaigns and sold as scrap, at 10–25% of what the material cost.

The money was invisible: it did not show up as a loss anywhere, only as "scrap revenue".

## What I built

1. **Synthetic dataset (Python).** 3,259 remnants over 18 months, with realistic rules: material and thickness mix, lognormal sizes, weight from density, reuse chances that depend on size and material, quarterly cleanup campaigns before the control process, and a 120-day scrap policy after it.
2. **Star schema in Power BI.** One fact table (remnants) and four dimensions (material, machine, location, calendar). The calendar has two relationships: the active one by creation date, and an inactive one by disposal date, used with `USERELATIONSHIP` to see *when* material left the stock.
3. **15 DAX measures**: stock (count, m², kg, BRL, age), outcome (reuse rate, scrapped kg, value lost to scrap, days to reuse) and timing.
4. **Two pages, each answering one business question:**
   - *Stock today:* what is on the racks, how old it is, where it is, and which pieces to use first.
   - *Reuse vs scrap:* are we reusing or scrapping, and did the control process help?
5. **Report as code.** The whole report (model, measures, 24 visuals, theme) is generated by a Python script in the Power BI Project format (TMDL + PBIR) and validated against Microsoft's JSON schemas. It is versioned in Git like any other code.

## Results (synthetic scenario)

| | Before control | After control |
|---|---|---|
| Reuse rate | 20.5% | 74.1% |
| Avg days to reuse | 65 | 28 |
| Value lost to scrap | BRL 105k in 10 months | BRL 22k in 8 months |

## What I learned

- A good KPI needs a clear denominator: the reuse rate only counts remnants that already left the stock, otherwise recent months look artificially bad.
- Role-playing dates (creation vs disposal) are easy to get wrong; an inactive relationship + `USERELATIONSHIP` keeps the model a simple star.
- Writing the report as code (PBIR) makes it reviewable and reproducible, the same way a data pipeline is.
